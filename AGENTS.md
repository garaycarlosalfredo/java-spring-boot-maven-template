# Agent instructions

Read [README.md](README.md) before modifying the project. It documents commands, functional status, and architecture rules.

## Status and scope

- The single Maven application uses a feature-based layered architecture. Do not assume planned features are implemented. Actuator health and liveness/readiness endpoints were implemented and manually verified against PostgreSQL 18.6 on 2026-11-07.
- The `items` POST validates input, invokes the item service, persists through Spring Data JPA, and returns `201` JSON with `Location`. Listing is implemented and was verified through HTTP after the service refactor. GET by ID is implemented and was verified through HTTP against local PostgreSQL on 2026-11-06 (`404` through the shared `ResourceNotFoundException`). PUT update by ID is implemented and was verified through HTTP against local PostgreSQL on 2026-11-06 (full replacement, `200` with the updated item, `404` through the shared `ResourceNotFoundException`). DELETE by ID is implemented and was verified through HTTP against local PostgreSQL on 2026-11-06 (physical delete, `200` confirmation containing only the deleted `id`, repeated delete `404` through the shared `ResourceNotFoundException`). Security is implemented as an adaptable baseline: every path except Actuator health requires HTTP Basic authentication against one in-memory user built from the required `APP_SECURITY_USERNAME` and `APP_SECURITY_PASSWORD` (no defaults; startup fails when missing or blank), the API is stateless with CSRF disabled and CORS not enabled, and rejections return Problem Details (`401` with a `WWW-Authenticate: Basic` challenge; `403` is configured but unreachable until roles exist). Actuator exposes only health, with public liveness and database-backed readiness probes and no health details; live verification against PostgreSQL 18.6 passed on 2026-11-07 and is recorded in the README "Verification history". A sample row survived a PostgreSQL container restart before the service refactor.
- Work in small steps: explain the change, implement it, verify it, and pause for review. Do not proceed through multiple planned stages without the user's instruction.
- Inspect current files and preserve existing changes. Do not regenerate or overwrite the project from Initializr.

## Implementation boundaries

- Use English throughout the repository: source file and directory names, packages, classes, methods, variables, JSON fields, routes, custom configuration identifiers, comments, error messages, logs, sample data, fixtures, and repository documentation. Conversation and external learning notes may remain in Spanish.
- Organize by feature, with layer subpackages inside each feature (`controller`, `service`, `repository`, `entity`, `dto`); never create empty packages. Keep application-wide error handling and shared exceptions in the `exception` package, and application-wide security configuration in the `security` package. The security rejection handler (`401`/`403` Problem Details) stays in `security` because those rejections happen in the filter chain, before MVC, so `ApiExceptionHandler` never sees them; it reuses the same Problem Details format. The structure and its rationale are in README "Architecture conventions".
- Name entities and repositories without a `Jpa` suffix (`Item`, `ItemRepository`). Use one controller per resource, with the base path on the class and a single test class with `@Nested` groups per operation. Services throw the shared `ResourceNotFoundException(resource, id)`; do not create one not-found exception per entity. A feature uses another feature only through its service, never its DTOs or entities.
- Controllers handle HTTP; services coordinate operations, business rules, and transactions; repositories handle persistence. Keep HTTP DTOs separate from persistence entities.
- Introduce external-service clients when needed, with configuration and error handling appropriate to the integration; follow the README "External service clients" conventions (unverified until the first real integration is added, and reviewed then). Add interfaces or separate domain models when they solve a concrete need, rather than by default.
- The example schema has PostgreSQL-generated incremental `BIGINT` id and unique sku, required nonblank name (100), optional description (1000), and required nonnegative `NUMERIC(12,2)` price. Model money with `BigDecimal`; HTTP validation uses Bean Validation and strips name edges before validation; price has at most 10 integer digits and 2 decimal places. Creation, listing, lookup by ID, update by ID, and deletion by ID are implemented.
- Keep business rules out of controllers and adapters. Add real business logic when required by the task.

## Verification and documentation

- Use Maven Wrapper from the repository root. Standard verification: `./mvnw verify`; use `./mvnw clean verify` when a clean build is needed.
- Run relevant checks and preserve previous behavior. Distinguish executed checks from expected results.
- Automate service and business-rule tests with mocks or test doubles, without a database. Test HTTP behavior with mocked services. Do not require PostgreSQL or Testcontainers for automated tests. The README "Testing strategy" section is the single reference for what is automated and what stays manual.
- Manually verify migrations and persistence against external local PostgreSQL as they are implemented, following the README "Testing strategy" manual checklist; record steps and results. Automated database integration tests are a decision for derived projects (isolation guidance is in the same section).
- JPA/Hibernate and the PostgreSQL driver are configured in the Maven application. Supply `DB_URL`, `DB_USERNAME`, required `DB_PASSWORD`, and required `APP_SECURITY_USERNAME` and `APP_SECURITY_PASSWORD` locally. Keep `ddl-auto=none`; Flyway migrations own the schema. Applied migrations must not be rewritten; add a new version.
- Current automated tests check the HTTP contract and business rules with mocks, as listed in the README "Testing strategy". They do not prove full application startup or database connectivity. Live connection/startup and V1 migration/restart checks passed on 2026-10-26; future persistence changes still need live verification.
- PostgreSQL runs in an external Docker environment that may be shared with other services. This application owns the schema and migrations; other services must not migrate the shared schema. Do not read or copy the Docker repository's `.env` or credentials.
- Run `spring-boot:run` from the repository root as documented in README.
- If you start the application for a manual check, stop it when the check ends and confirm the port is free. Stop it by the exact PID of the process you started (find it with `ss -ltnp`); do not use `pkill` or other pattern-based kills. Mention in the report if the user's own instance was left untouched.
- Keep datasource and JPA settings in `src/main/resources/application.properties`; use native Spring configuration import to read local `.env` as Java properties. Do not add custom startup scripts. Keep `TEMPLATE:` comments where derived projects adapt environment configuration. Run from the repository root; the Boot Maven plugin uses that directory. Commit only `.env.example` with generic unquoted placeholders. Do not open, print, overwrite, or copy local `.env` contents or credentials.
- CI (`.github/workflows/ci.yml`) runs only on pushes to `development` and on pull requests; it deliberately does not run on `main`. This is a decision of the repository owner: do not add `main` to the triggers, and do not raise it as a gap or ask about it again.
- Keep README and code synchronized. Do not mark a feature complete when its verification is pending.
- Do not store secrets or real data in configuration, examples, fixtures, or logs.
